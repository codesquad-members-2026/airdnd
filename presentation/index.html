검색

100만 건에서 숙소 하나를 찾는 데
왜 7초가 걸렸나 — 그리고 어떻게 ms로 줄였나
검색 ① — 증상과 진단

"100만 중 1개 검색이 7초"

7s
한 개의 느린 검색처럼 보였지만
사실 여러 문제가 쌓여 있었다
Layer 1 · 풀스캔

비-sargable LIKE

region 검색이 LIKE '%term%' + lower() → B-tree 인덱스를 못 탐

Layer 1 · 인덱스 부재

region 인덱스가 없었다

유일한 선별 필터인데 인덱스 자체가 없어 매 검색이 ~1M행 스캔

Layer 3 · PK 워크

ORDER BY id … LIMIT

MySQL을 PK 워크로 유도 → 매칭이 희소하면 사실상 전체 스캔

검색 ② — 공간 인덱스로 전환

1D 인덱스로는 2D 문제를 못 푼다

전환

POINT + R-tree SPATIAL

위·경도를 공간 컬럼으로 묶고 공간 인덱스 적용 V9 → V10

함정 ①

SRID 0 제약 필수

컬럼을 SRID 0으로 제약해야 MySQL이 공간 인덱스를 사용

함정 ②

술어는 bare로 emit

MBRContains(...)=1로 감싸면 옵티마이저가 못 봄 → 그냥 풀스캔

7s → ~ms
두 함정을 고치자
검색 응답이 밀리초 단위로

// region 검색 — 한 줄 차이 room.region.containsIgnoreCase(region) // LIKE '%term%' room.region.startsWith(region) // LIKE 'term%' // → idx_rooms_region 사용 (sargable prefix) // 공간 술어는 bare로 emit (=1로 감싸지 않음) mbrcontains(ST_GeomFromText({0}, 0), room.location) // → idx_rooms_location 사용
한 줄이 풀스캔이냐 인덱스냐를 가른다

검색 ③ — 성숙한 결론

전역 힌트는 답이 아니었다

시도 · FORCE INDEX 등가

빈 / 희소 박스 → ms

ORDER BY id+0 트릭으로 인덱스를 강제 → 빈 바다 패닝이 밀리초로 개선

그러나 · 퇴행

밀집 박스 → 1~2s

줌아웃한 밀집 영역이 filesort로 오히려 느려짐 → 되돌림

왜 한 방에 안 되나

plain-PK와 filesort는 정반대 병리 — 전역 ORDER BY 하나로는 둘 다 이길 수 없다.

진짜 해법

박스 크기 · 예상 행 수에 따라 접근 경로를 고르는 적응형. 멋진 힌트가 아니라 올바른 진단.

결제 ② — 해법과 결과

PayPal 호출을 락 밖으로

짧은 트랜잭션 — 락 + 재검증 + CAPTURING 마킹 → 커밋과 함께 락 해제
락 없이 PayPal 호출 — 더 이상 Room 락·DB 커넥션을 쥐지 않음
짧은 트랜잭션 — 예약 확정 + CAPTURED + 이벤트
왜 안전한가

이중예약을 막는 건 Room 락이 아니라 PENDING 홀드 — 락을 풀어도 슬롯은 선점됨.

That browser crash (Chrome's "error code 5" is a renderer OOM) plus the 32s response is the cliff we predicted: the backend serialized a huge SELECT * result and the frontend's O(n²) clusterRooms tried to chew through tens of thousands of points. That's the proof. Here's the full plan to fix it properly.

First, the root cause in one line: the list and the map share one unbounded, full-entity query, and there's no geo index. The fix is to (a) index the geo lookup, (b) split into two purpose-built endpoints, and (c) make the map aggregate server-side. Below is a phased plan — each phase is independently shippable and verifiable.

Phase 1 — DB schema: index the bbox (the single biggest win)

New Flyway migration V5__add_rooms_geo_index.sql:

-- Bbox range scan support. Leading column = latitude (range-narrowed),
-- longitude read via index-condition pushdown. price_per_night included so the
-- map aggregation (MIN/MAX price + COUNT) can run index-only, no row lookups.
CREATE INDEX idx_rooms_lat_lng_price
  ON rooms (latitude, longitude, price_per_night);

Keep latitude/longitude as DECIMAL(15,12) for now. A plain B-tree composite already turns the 1.1M-row full scan into a narrow range scan — that almost certainly closes the gap you measured. Converting to POINT + SPATIAL (R-tree) is a real win only at the millions-of-rows-with-radius-search level; I've put it in Phase 5 as optional, because it's a heavier migration (SRID, MBRContains query rewrite, NOT NULL backfill) and shouldn't block the split.

Verify before/after with the file you already have (apps/backend/scripts/perf_room_search.sql): re-run the C1 Seoul-bbox case. The top node should flip from Table scan on rooms (actual rows=1.1e6) to an index range scan with actual rows near the matched count.

Phase 3 — Backend map endpoint (points-or-clusters hybrid)

New GET /api/rooms/map?south&west&north&east&...filters...&cols=24.

Service logic:
1. Run a COUNT(*) over the bbox+filters (index-backed, fast).
2. If count ≤ POINT_THRESHOLD (e.g. 500): return mode="points" with a slim list [{e, rating}]. The existing client clustering can handle ≤500 fine.
3. Else return mode="clusters": server-side grid aggregation. Service computes celLng=(east-west)/cols (so buckets ≤ rows*cols ≈ a few hundred regardless of room
count), then:
SELECT FLOOR((latitude  - :south)/:cellLat) AS gy,
       FLOOR((longitude - :west )/:cellLng) AS gx,
       COUNT(*) AS cnt, AVG(latitude) AS lat, AVG(longitude) AS lng,
       MIN(price_per_night) AS min_price, MAX(price_per_night) AS max_price
FROM rooms
WHERE latitude BETWEEN :south AND :north
  AND longitude BETWEEN :west AND :east
  AND is_active AND NOT is_deleted
  -- + the same filter predicates as the list
GROUP BY gy, gx;
3. Response: mode="clusters", [{lat, lng, count, minPrice, maxPrice}].

This is cleanest as a small native query (the FLOOR(...) grouping is awkward in Quns.numberTemplate if you prefer to keep it typed). v1 uses a per-viewport grid(simple); if cluster "jumping" on pan bothers you, switch to a fixed global geohash grid per zoom later.
